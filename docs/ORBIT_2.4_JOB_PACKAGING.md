# Orbit 2.4 · 岗位包装与面试材料

目标岗位：**深圳市黑蚂蚁软件有限公司 · AI 教育应用开发助理工程师**（3 人，5000–7000 元/月）。

公司做教育数字化与 AI 教育应用，客户是中小学、幼儿园、高中与教育相关单位；岗位要求大专及以上，会至少一门语言（Java / Python / JavaScript / TypeScript），了解 Web、数据库、API，用过 Claude、Codex 等 AI 工具，对 AI 编程、Agent、大模型应用有兴趣。

Orbit 2.4 的定位不是「又一个记账 App」，而是**一套能讲清楚端到端取舍的学生学习产品**：Android 客户端、云端账号与同步、AI 规划与周复盘、Coze 智能体、结构化输出校验与配额。下面把每一条岗位要求落到可演示、可追问的证据上。

## 1. 岗位要求 → 项目证据

| 岗位原文 | Orbit 里的证据 | 面试时怎么讲 |
| --- | --- | --- |
| 至少了解一种编程语言 | Kotlin（Android 全量业务）+ JavaScript（uniCloud 云函数，零 npm 依赖） | 不是「学过语法」，而是用两门语言交付了同一套 REST 契约：客户端 Retrofit、服务端 Node 18 原生 `http`/`fetch` |
| 了解 Web、数据库、API | Bearer 鉴权、REST 路由、错误体、epoch day 语义、Room + 云数据库、快照 revision CAS | 先讲「为什么整包快照 + revision」：学生数据量小、离线优先，整包比字段级合并简单且可回滚；再讲 409 冲突如何用最新快照覆盖本地 |
| 使用过 Claude、Codex 等 AI 工具 | 项目从需求、实现到测试都用 AI 编程工具推进；仓库里有提示词、测试与文档 | 讲「怎么让 AI 产出可合并的代码」：先定契约与测试，再让 AI 写实现；生成后自己跑测试、看截图、修边界 |
| 对 AI 编程、Agent、大模型应用有兴趣 | Coze Bot + PAT、提示词版本化（`plan-v1` / `review-v1`）、结构化 JSON 校验、一次修复重试、25 秒预算、按用户每日配额 | 这是全场最匹配的一段：不是「调通 API」，而是把不稳定的模型输出变成一个可以写进数据库的产品功能 |
| 教育场景理解 | 学习目标拆解为阶段 / 任务、周复盘围绕完成率 / 习惯 / XP、导入后仍是普通任务可修改 | 讲「AI 只生成一次，之后回到可编辑的数据」：教育产品不能让模型成为黑箱，老师 / 学生要能改 |

## 2. 3 分钟演示脚本

准备：一台装有 2.4.0 APK 的 Android 手机（或模拟器），已登录演示账号，Coze 环境变量已配置。

1. **0:00–0:20 开场**
   「这是我做的一个学生学习规划 App，叫 Orbit。它把任务、目标、习惯和成长记录放在一起，2.4 加了 AI 规划与周复盘。后端在 uniCloud 支付宝云，AI 走 Coze Bot，令牌只在云函数里。」
2. **0:20–1:10 目标页 → AI 规划**
   点目标页的 `AI` 卡片，填一个真实目标（示例：三个月内掌握 Android 开发，能独立完成并上架一个应用；每天 60 分钟；当前水平「会 Kotlin 基础语法」；薄弱点「状态管理、接口联调」）。点生成，展示等待卡与结果。
   讲一句：「模型只返回相对天数，服务端换算成 epoch day，并限制 1–6 个阶段、每阶段 1–5 个任务、总计 20 个；输出不合法会自动修复一次。」
3. **1:10–1:40 预览与导入**
   取消一两个任务，点导入，自动跳到目标详情页。
   讲：「导入是一个 Room 事务，写目标、阶段和任务；任务分类固定学习，不写成长流水，避免导入就刷 XP。AI 生成完就退出，后面都能手改。」
4. **1:40–2:20 完成任务 → 成长页周复盘**
   完成一个学习任务、打一次习惯卡，回到成长页，点「生成本周复盘」。
   讲：「发给模型的只有聚合数据：计划 / 完成数、学习任务数、习惯可能天数 / 打卡数、XP、最多 8 个目标的标题与进度；不发任务标题和备注。结果按用户 + 周一缓存在本机，退出登录会清掉。」
5. **2:20–2:50 工程细节**
   打开设置里的关于页 / 或直接讲：「AI 每个账号每天规划 6 次、复盘 4 次，按北京时间；额度在调用模型前扣减，失败也算，因为上游成本已经发生。令牌 30 天，只存在云函数环境变量，APK 里没有。」
6. **2:50–3:00 收尾**
   「项目有 Node 49 项、JVM 96 项、设备 48 项测试；接口文档是 OpenAPI，排障和 Coze 搭建步骤都写在 docs 里。我想做的是把 AI 能力变成教育产品里稳定、可解释的一小块。」

演示失败预案：AI 未配置或超时，就直接展示「AI 暂不可用」状态与失败文案，说明「这就是产品的一部分：模型不可用时，记任务、目标、习惯全部照常工作」。然后打开 `docs/openapi-orbit.yaml` 或截图讲契约。

## 3. 简历项目条目

> 按「做了什么 + 如何实现 + 结果」写，突出 ownership、取舍与验证；数字用可核对的测试数量，不虚构用户量。

**Orbit · 学生学习规划 Android 应用（个人项目）**

- 独立完成 Android 客户端与 uniCloud 云函数：五标签任务 / 目标 / 习惯 / 成长体系，Room 离线缓存 + 云端整包快照同步，Bearer 鉴权、revision CAS 冲突覆盖与账号数据隔离。
- 设计并实现 AI 学习规划与周复盘：Coze Bot 经云函数转发，提示词版本化，服务端把模型的相对天数规范化为 epoch day，限制阶段 / 任务数量与优先级枚举；JSON 不合法时自动修复一次，再失败返回可展示的错误。
- 为 AI 链路补上产品级约束：按北京时间每账号每日 6 次规划 / 4 次复盘，调用前扣减；25 秒预算与超时、繁忙、未配置、输出不合法分别映射为不同文案；周复盘只发送聚合指标，结果按用户 + 周一缓存并在退出登录时清除。
- 交付 OpenAPI 3.0 接口文档、Coze 搭建手册与排障表；Node 49 项、JVM 96 项、设备 48 项测试通过，覆盖日期换算、配额、错误映射、导入事务与 UI 关键路径。

若简历空间只够两条：

- 用 Kotlin + uniCloud 云函数交付学生学习 App：Room 离线缓存、Bearer 鉴权、快照 revision 同步，导入 AI 计划时以单事务写目标 / 阶段 / 任务。
- 接入 Coze 实现 AI 规划与周复盘：提示词版本化、结构化输出校验与一次修复、按用户每日配额、超时 / 繁忙 / 未配置降级，令牌仅存云函数环境变量。

## 4. 面试问答

### Q1：为什么用 Coze，而不是自己训练模型或直接调 OpenAI？

「这个岗位要做的是 AI 教育应用，不是模型研究。Coze 提供现成的 Bot 编排、发布渠道和配额管理，我能把精力放在产品契约、数据规范化和失败降级上。直接调大模型也可以，但一样要在服务端做鉴权、提示词版本、结构化校验和配额；换成任何一家模型，`AiRepository` 和 UI 都不用改。真正的取舍是：先用托管平台验证场景，等有稳定的教育场景和数据，再考虑换模型或做 RAG。」

### Q2：为什么令牌不放在 App 里？

「APK 可以被反编译，任何写进客户端的密钥都等于公开。Coze PAT 放在 uniCloud 云函数的环境变量里，客户端只认 Orbit 自己的 `/api/ai/*`；云函数做登录校验、配额和输入裁剪，令牌不出服务端。代价是多一跳网络和一次 Node 解析，但这是必须付的成本。」

### Q3：模型输出不稳定怎么办？

「三层：第一层是提示词，明确只输出 JSON、字段、枚举和长度；第二层是服务端规范化，阶段 1–6、每阶段任务 1–5、总计 20 个，日期偏移夹取，阶段结束日单调，优先级只认三个值；第三层是失败处理，第一次不合法就把错误原因拼成修复消息再请求一次，仍失败返回 502 `AI_INVALID_OUTPUT`，不写库。客户端保留上一份预览，不会因为一次失败把用户输入清掉。」

### Q4：为什么额度在调用前扣，失败了也算？

「上游成本在请求发出时就发生了，失败重试如果免费，用户可以通过故意触发失败绕过上限。产品上要在按钮旁明确写「今日还可生成 N 次」，并说明失败也会消耗；如果未来要做补偿，应该由服务端按 requestId 做幂等返还，而不是客户端重试。」

### Q5：为什么不用流式输出？

「Coze 的 v3 非流式接口是创建会话、轮询、拉消息列表，25 秒内拿不到就判超时。流式体验更好，但规划结果需要完整 JSON 才能校验和导入，半截 JSON 对用户没有价值；周复盘文字短，等待卡足够。以后如果做对话式辅导，再单独做流式通道。」

### Q6：整包快照同步会不会丢数据？

「不会丢已提交的数据，但会丢并发写入：服务端是权威，revision 不匹配时返回 409 和最新快照，客户端用最新快照覆盖本地，再让用户重做刚才的修改。学生数据量小、单账号多设备场景少，整包比字段级合并简单、可回滚；如果以后做多人协作，才需要 CRDT 或操作日志。」

### Q7：AI 生成的学习计划质量怎么保证？

「服务端只能保证结构和边界，内容质量要靠提示词与验收。当前限制目标 60 字、每日 10–480 分钟、目标日期 730 天内，并要求阶段有递进、任务可执行、优先级合理；导入后是普通任务，学生可以改。下一步会用一批真实目标做离线评测，看阶段数、任务粒度、日期分布是否合理，而不是只看 JSON 能不能解析。」

### Q8：教育场景的数据隐私你怎么考虑？

「周复盘只发聚合数字和目标标题，不发任务备注；密码 scrypt、令牌只存 SHA-256、30 天过期；AI 结果只缓存在本机，退出登录清除。真正商用还要补隐私政策、未成年人保护、数据删除接口和学校侧的授权流程，这些不是个人项目能拍脑袋决定的。」

### Q9：这个项目最大的不足是什么？

「三點：第一，真实 Coze 调用还在等环境变量配置，目前只有单测和假客户端验证；第二，没有真实用户，AI 计划的教育有效性没有数据；第三，客户端只做了 Android，Web 端和老师侧都没有。下一步优先补真机 E2E 和一批真实目标评测，再考虑 Web。」

### Q10：如果让你在这个公司做第一个功能，你会怎么做？

「先跟着现有产品的数据模型和接口规范走，不另起一套。比如要做「按班级布置学习计划」，我会先确认班级、学生、计划的实体和权限边界，再复用 Orbit 里的模式：AI 只生成草稿，老师确认后写库；输出结构化、可修改、有配额和失败降级。先做小闭环，再谈 Agent。」

## 6. 面试前一周的补强（可选）

1. 配好 Coze 环境变量，跑通真实计划与复盘，录一段 60 秒屏录；把「真实调用通过」写进 README 与本文档。
2. 用 5 个真实学习目标各生成一次，记录阶段数、任务数、日期分布与明显不合理的输出，作为「评测」而不是「感觉」来讲。
3. 把 `docs/openapi-orbit.yaml` 导入 Apifox，演示一次鉴权、409 冲突与 AI 配额错误；这比背概念更能证明 API 基础。
4. 准备一个 30 秒的「如果重做」回答：先做 Web 端教师视图，还是先做真实用户访谈？答案不重要，重要的是有判断依据。

> 诚实边界：截至 2.4.0，真实 Coze 调用与真机 E2E 尚未执行，原因是 Coze 令牌需要账号持有人自行配置，不能写进代码或交给他人。面试时主动说明这一点，并展示 `configured:false` 的降级状态与错误映射，比声称「全部跑通」更可信。
