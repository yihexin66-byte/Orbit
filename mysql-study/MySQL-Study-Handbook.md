## 1. 索引

### 1.1 一句话

索引是**有序的数据结构**，用额外的存储和写入成本，换查询时更少的磁盘 IO。

### 1.2 B+ 树

InnoDB 以页（默认 16KB）为单位读写磁盘。

- 非叶子节点：只存键和子页指针，不存整行 → 扇出大、树矮。
- 叶子节点：存数据（聚簇索引）或主键值（二级索引），并按顺序用双向链表连接。
- 树高通常 3～4 层，就能覆盖千万到十亿级数据，具体取决于行大小和主键长度。
- 范围查询：先定位到起点，再沿叶子链表顺序扫描，不用回到根节点。

```
                 [ 10 | 20 | 30 ]                 非叶子：只存 key + 指针
                /       |       \
          [<10]      [10,20]      [20,30]
             |           |            |
         leaf <-> leaf <-> leaf <-> leaf           叶子：有序双向链表
```

**为什么不用其他结构**

| 结构 | 问题 |
| --- | --- |
| B 树 | 非叶子也存数据，扇出小，树更高；范围查询要在层间跳 |
| 哈希 | 只适合等值查询，不支持范围、排序、最左前缀 |
| 红黑树 | 内存结构，树高随数据量增长，磁盘 IO 次数多 |
| 跳表 | 常见于内存索引（如 Redis），磁盘页管理不如 B+ 树 |

### 1.3 聚簇索引、二级索引与回表

| 类型 | 叶子存什么 | 说明 |
| --- | --- | --- |
| 聚簇索引 | 整行数据 | 主键索引；一张表只有一个 |
| 二级索引 | 主键值 | 查索引之外的列要回表 |
| 覆盖索引 | 查询需要的列 | 索引里已有全部列，不回表 |

- 没有主键时，InnoDB 选第一个非空唯一索引；还没有就生成隐藏 `row_id`。
- 回表：二级索引找到主键 → 再去聚簇索引查整行。
- 覆盖索引：`EXPLAIN` 的 `Extra` 出现 `Using index`。
- 二级索引的叶子存主键，所以主键越长，所有二级索引越大。

```sql
-- 假设 idx_user_id(user_id)
SELECT id, title FROM sync_tasks WHERE user_id = 7;
-- 1. idx_user_id 找到主键 id
-- 2. 回表到聚簇索引取 title

-- 假设 idx_user_title(user_id, title)
SELECT id, title FROM sync_tasks WHERE user_id = 7;
-- title 在索引里，覆盖索引，不回表
```

### 1.4 联合索引与最左前缀

```sql
KEY idx_ust (user_id, status, created_at)
```

索引按 `user_id`、`status`、`created_at` 依次排序。查询必须从最左列开始连续使用，才能用于定位。

| SQL | 能用于定位的列 | 说明 |
| --- | --- | --- |
| `WHERE user_id=? AND status=? AND created_at>?` | 三列 | 等值 + 范围，理想 |
| `WHERE user_id=? AND status=? ORDER BY created_at` | 三列 | 排序也能用索引，无 filesort |
| `WHERE user_id=? AND created_at>?` | `user_id` | `status` 缺失，`created_at` 不能继续定位，最多 ICP 过滤 |
| `WHERE status=? AND created_at>?` | 无 | 跳过最左列，通常全表/全索引扫描 |
| `WHERE user_id=? ORDER BY created_at` | `user_id` | `status` 不固定，整体顺序不是 `created_at`，通常 filesort |
| `WHERE user_id=? AND status IN (?,?) ORDER BY created_at` | `user_id`、`status` | 多个 status 的 `created_at` 交错，通常 filesort |

**设计顺序的经验**

- 等值条件放前面，范围条件放后面；
- 排序字段尽量接在等值字段后面；
- 区分度高的列优先，但查询模式比“区分度”更重要；
- 不要机械追求“区分度最高的列放第一”，否则可能破坏最左前缀和排序。

### 1.5 索引失效 / 不走索引

⚠ 这些不是“绝对失效”，而是“通常无法有效使用，优化器可能全表扫”。

1. 列上做函数或运算：`WHERE DATE(created_at)=...`、`WHERE id+1=...`。
2. 隐式类型转换：`varchar_col = 123` 会把列转成数字；`int_col = '123'` 通常只是常量转换，影响较小。
3. 前导模糊：`LIKE '%abc'`；`LIKE 'abc%'` 可以。
4. `OR` 两边不都有索引；有时会走 index merge，但不稳定。
5. 联合索引不满足最左前缀。
6. 范围列之后的列不能继续用于定位/排序。
7. 负向条件、低区分度列，优化器算完成本可能直接全表扫。
8. 表很小、回表比例很高、需要读取大部分行时，全表扫可能更快。
9. 统计信息过期，优化器选错索引；可 `ANALYZE TABLE` 更新统计。
10. 索引列参与计算、类型不一致、字符集/排序规则不一致，也可能导致无法使用。

### 1.6 EXPLAIN 看什么

| 列 | 关注点 |
| --- | --- |
| `id` | 执行顺序；id 越大越先执行，相同 id 从上到下 |
| `select_type` | SIMPLE / PRIMARY / SUBQUERY / DERIVED / UNION |
| `type` | `system > const > eq_ref > ref > range > index > ALL` |
| `possible_keys` | 候选索引 |
| `key` | 实际使用的索引；为 NULL 说明没走索引 |
| `key_len` | 使用到的索引字节数；可判断联合索引用了几列 |
| `ref` | 与索引比较的列/常量 |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤后剩余百分比 |
| `Extra` | 关键信息，见下表 |

| Extra | 含义 |
| --- | --- |
| `Using index` | 覆盖索引，不回表 |
| `Using index condition` | 索引下推（ICP），在存储引擎层过滤 |
| `Using where` | 从引擎取回后再过滤 |
| `Using filesort` | 无法用索引排序，额外排序 |
| `Using temporary` | 使用了临时表，常见于 GROUP BY / DISTINCT / UNION |
| `Using join buffer` | 被驱动表没有可用索引，使用连接缓冲 |

```sql
EXPLAIN
SELECT id, title
FROM sync_tasks
WHERE user_id = 7 AND status = 'TODO'
ORDER BY due_at;
```

- 理想：`key` 命中联合索引，`rows` 不大，`Extra` 没有 `Using filesort` / `Using temporary`。
- 需要看实际执行：MySQL 8.0.18+ 可用 `EXPLAIN ANALYZE`。
- 查看索引统计：`SHOW INDEX FROM sync_tasks;`。

### 1.7 设计索引的流程

1. 找慢查询：慢查询日志、`performance_schema`、APM。
2. 看 SQL 的 WHERE、JOIN、ORDER BY、GROUP BY。
3. 设计联合索引：等值在前，范围在后，尽量覆盖查询列。
4. 用 `EXPLAIN` 验证 `key`、`rows`、`Extra`。
5. 评估写入成本：每个索引都要维护 B+ 树，不是越多越好。
6. 上线后观察慢查询和写入延迟；必要时用 8.0 的 invisible index 安全下线。
7. 定期清理冗余索引（前缀重复、最左列重复）。

### 1.8 高频面试题

#### Q1 ★ 为什么 MySQL 用 B+ 树，不用 B 树、哈希、红黑树？

**参考回答（30 秒）**：B+ 树非叶子只存键，扇出大、树矮，磁盘 IO 少；叶子有序且链表连接，范围查询和排序友好。B 树非叶子存数据，扇出小、树高；哈希只支持等值查询；红黑树是内存结构，树高和数据量线性相关，磁盘 IO 太多。

**追问**：为什么非叶子不存数据？→ 为了在同样 16KB 页里放更多键，降低树高，减少 IO。

#### Q2 ★ 聚簇索引和二级索引有什么区别？什么是回表？

**参考回答**：聚簇索引的叶子存整行，主键索引就是聚簇索引；二级索引的叶子存主键值。查询二级索引时，如果需要的列不在索引里，就要拿主键回聚簇索引再查一次，这叫回表。把查询列放进联合索引，形成覆盖索引，就能避免回表。

**追问**：没有主键怎么办？→ 选第一个非空唯一索引，否则用隐藏 row_id。

#### Q3 ★ 什么是最左前缀原则？联合索引 `(a,b,c)` 哪些查询能用？

**参考回答**：联合索引按 a、b、c 依次排序，查询必须从最左列开始连续使用。`a=?`、`a=? AND b=?`、`a=? AND b=? AND c=?` 都能用；`b=?` 或 `b=? AND c=?` 用不上；`a=? AND c=?` 只能用 a 定位，c 最多做索引下推过滤，不能用于缩小扫描范围。

**追问**：`a=? AND b>? AND c=?` 呢？→ a、b 用于定位，c 不能继续定位，可能 ICP 过滤。

#### Q4 ★ 什么是覆盖索引？怎么优化回表？

**参考回答**：查询需要的列全部在索引里，不需要回表，`EXPLAIN` 显示 `Using index`。优化方式是把高频查询的返回列加入联合索引，但要权衡索引大小和写入成本；不要为了覆盖而盲目 `SELECT` 很多列。

**追问**：`SELECT *` 为什么容易慢？→ 很难覆盖，通常要回表，还会传输无用列。

#### Q5 ★ 索引失效的常见场景有哪些？

**参考回答**：列上做函数/运算、隐式类型转换、前导 `%` 模糊、`OR` 两边不都有索引、联合索引不满足最左前缀、范围列之后的列、低区分度或负向条件、表太小优化器选择全表扫、统计信息过期。

**追问**：`LIKE 'abc%'` 能用吗？→ 能；`LIKE '%abc'` 不能有效使用。

#### Q6 索引越多越好吗？

**参考回答**：不是。每个索引都要占空间、增加插入/更新/删除的维护成本，还会让优化器选择变多。索引应该由查询驱动，定期清理冗余索引。

#### Q7 主键为什么建议自增？UUID 有什么问题？

**参考回答**：自增主键顺序写入，减少页分裂和碎片；UUID 随机写入会导致页分裂、索引碎片，且主键更长会让所有二级索引变大。分布式场景可以用趋势递增的 Snowflake 或有序 ID，而不是随机 UUID。

#### Q8 ★ 深分页怎么优化？

**参考回答**：`LIMIT 1000000, 20` 会扫描并丢弃大量行。可以用游标分页 `WHERE id > last_id ORDER BY id LIMIT 20`；或者延迟关联：先用覆盖索引查出主键，再回表取数据；同时保证排序字段有索引。

**追问**：为什么游标分页不适合跳页？→ 它依赖上一页的最后一条记录，不能随机跳到第 N 页。

#### Q9 ★ EXPLAIN 重点看什么？

**参考回答**：先看 `type` 是否到 `range/ref/const`，避免 `ALL`；再看 `key` 是否命中预期索引；然后看 `rows` 和 `filtered` 估算；最后看 `Extra`，`Using index` 是覆盖索引，`Using filesort` 和 `Using temporary` 需要关注。

#### Q10 一张表怎么设计索引？

**参考回答**：先收集高频 SQL 和慢查询，按 WHERE/JOIN/ORDER BY 设计联合索引；等值在前、范围在后，尽量覆盖；用 EXPLAIN 验证；控制索引数量并观察写入成本；上线后持续清理冗余索引。

### 1.9 易错点

- ⚠ 联合索引 `(a,b,c)` 中，`WHERE a=? AND c=?` 不是“完全用不上”，而是 a 用于定位、c 可能 ICP 过滤。
- ⚠ `varchar_col = 123` 和 `int_col = '123'` 不一样：前者列被转换，后者通常只是常量转换。
- ⚠ `IS NULL` 可以使用索引，不要说“NULL 不能建索引”。
- ⚠ `ORDER BY` 想用索引，需要顺序匹配、方向一致，且中间不被范围条件打断。
- ⚠ 索引区分度低不代表一定没用，联合索引和覆盖索引场景仍可能有价值。
- ⚠ 优化器是成本驱动的，索引存在不等于一定使用。

### 1.11 速记

- B+ 树：矮胖、有序、范围快。
- 聚簇存整行，二级存主键；查索引外的列要回表。
- 联合索引最左前缀；等值在前，范围在后。
- 覆盖索引看 `Using index`。
- 失效清单：函数、隐式转换、前导 `%`、OR、顺序、低选择性。
- EXPLAIN 四看：type、key、rows、Extra。

## 2. 事务

### 2.1 一句话

事务把多条语句打包成一个原子单元；InnoDB 用 undo/redo、锁和 MVCC 共同保证 ACID。

### 2.2 ACID 由谁保证

| 特性 | 实现 |
| --- | --- |
| 原子性 Atomicity | undo log：失败时回滚 |
| 一致性 Consistency | 约束、应用逻辑，以及 A/I/D 共同保证 |
| 隔离性 Isolation | 锁 + MVCC |
| 持久性 Durability | redo log（WAL）+ 刷盘 |

### 2.3 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | 有 | 有 | 有 | 基本不用 |
| 读已提交 RC | 无 | 有 | 有 | Oracle 默认；互联网业务常用，gap lock 少 |
| 可重复读 RR | 无 | 无 | InnoDB 下快照读无，当前读靠 next-key | MySQL 默认 |
| 串行化 Serializable | 无 | 无 | 无 | 读也加锁，性能最差 |

- 脏读：读到别的事务未提交的数据。
- 不可重复读：同一事务两次读同一行，结果不同。
- 幻读：同一事务两次范围查询，第二次多出/少了行。

### 2.4 MVCC

**隐藏列**

InnoDB 每行有：

- `DB_TRX_ID`：最后修改该行的事务 ID；
- `DB_ROLL_PTR`：指向 undo log 中的旧版本；
- 没有主键时还有隐藏 `DB_ROW_ID`。

**版本链**

```
当前行 [trx_id=80] --roll_ptr--> undo [trx_id=70] --> undo [trx_id=60] --> ...
```

**ReadView**

事务做快照读时生成 ReadView，包含：

- `m_ids`：生成时仍活跃的事务 ID 列表；
- `min_trx_id`：活跃事务中的最小 ID；
- `max_trx_id`：下一个将分配的事务 ID；
- `creator_trx_id`：当前事务 ID。

判断某个版本是否可见：

| 条件 | 是否可见 |
| --- | --- |
| `trx_id == creator_trx_id` | 可见（自己的修改） |
| `trx_id < min_trx_id` | 可见（已提交） |
| `trx_id >= max_trx_id` | 不可见（视图创建后才开始） |
| `min_trx_id <= trx_id < max_trx_id` 且 `trx_id` 在 `m_ids` 中 | 不可见（仍活跃） |
| 其他 | 可见（已提交） |

**RC 与 RR 的差别**

- RC：每条快照读语句都新建 ReadView，所以同一事务两次查询可能不同。
- RR：事务第一次快照读时创建 ReadView，之后复用，所以可重复读。

**快照读 vs 当前读**

| 类型 | 语句 | 行为 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | 读 ReadView 对应的历史版本，不加锁 |
| 当前读 | `SELECT ... FOR UPDATE`、`FOR SHARE`、`UPDATE`、`DELETE`、`INSERT` | 读最新已提交版本并加锁 |

### 2.5 RR 解决幻读了吗？

- 快照读：靠 MVCC，不会看到别的事务新插入的行。
- 当前读：靠 next-key lock，阻止范围内插入。
- 但存在经典例外：事务先做快照读，别的事务插入并提交，然后本事务执行 `UPDATE`（当前读）作用到了新行；之后快照读就能看到它。
- 所以标准回答是：**InnoDB 在 RR 下很大程度避免了幻读，但不是绝对；取决于读方式，快照读靠 MVCC，当前读靠锁。**

### 2.6 三种日志

| 日志 | 层次 | 作用 | 特点 |
| --- | --- | --- | --- |
| redo log | InnoDB | 崩溃恢复、持久性 | 物理日志，WAL，循环写 |
| undo log | InnoDB | 回滚、MVCC | 逻辑日志，版本链，长事务会膨胀 |
| binlog | Server | 归档、主从复制、PITR | 逻辑日志，row/statement/mixed |

**两阶段提交**

1. redo log 写入 prepare 状态并刷盘；
2. 写 binlog 并刷盘；
3. redo log 改为 commit。

崩溃恢复时：如果 binlog 完整，就提交；否则回滚。这样保证 redo 和 binlog 一致。

**“双 1”**

- `innodb_flush_log_at_trx_commit=1`：每次提交都刷 redo；
- `sync_binlog=1`：每次提交都刷 binlog；
- 持久性最好，但性能有代价；很多业务会结合组提交和压测调整。

### 2.7 长事务与 Spring 事务

**长事务的危害**

- 锁持有时间长，阻塞其他事务；
- undo 版本链变长，purge 延迟，历史版本膨胀；
- 主从延迟、内存和磁盘压力；
- 可能阻塞 DDL（MDL）。

**Spring `@Transactional` 常见坑**

| 坑 | 说明 |
| --- | --- |
| 同类自调用 | 代理不生效，事务注解失效 |
| private/final 方法 | 代理无法覆盖 |
| 异常被吞 | 事务感知不到异常，不会回滚 |
| 受检异常 | 默认不回滚，需要 `rollbackFor` |
| `readOnly=true` | 只是优化提示，不代表一定走只读库 |
| 事务里做 RPC/文件上传 | 事务变长，连接占用 |
| 异步线程 | 事务上下文不会自动传递 |

**传播行为速记**

- `REQUIRED`：有事务就加入，没有就新建（默认）；
- `REQUIRES_NEW`：挂起当前事务，新建独立事务；
- `NESTED`：嵌套事务，基于 savepoint；
- `SUPPORTS` / `NOT_SUPPORTED` / `MANDATORY` / `NEVER`：按字面理解。

### 2.8 高频面试题

#### Q1 ★ ACID 怎么实现？

**参考回答**：原子性靠 undo log 回滚；持久性靠 redo log 和刷盘；隔离性靠锁和 MVCC；一致性由约束、应用逻辑以及前三者共同保证。

#### Q2 ★ 隔离级别有哪些？MySQL 默认是哪个？

**参考回答**：RU、RC、RR、Serializable。MySQL InnoDB 默认 RR；很多互联网业务用 RC，因为 gap lock 少、死锁概率低，配合 row 格式 binlog 也安全。

**追问**：RC 和 RR 的核心区别？→ ReadView 创建时机不同：RC 每条语句新建，RR 第一次快照读创建并复用。

#### Q3 ★ MVCC 的原理是什么？

**参考回答**：InnoDB 行上有 `DB_TRX_ID` 和 `DB_ROLL_PTR`，修改旧版本写入 undo，形成版本链。快照读时生成 ReadView，根据事务 ID 和活跃事务列表判断版本是否可见。RC 每条语句新建视图，RR 复用第一次的视图，所以 RR 可重复读。

**追问**：ReadView 里有什么？→ `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id`。

#### Q4 ★ 为什么 RR 能可重复读？

**参考回答**：RR 在事务第一次快照读时创建 ReadView，之后一直复用。后续快照读都按同一个视图判断版本，看不到视图创建后其他事务提交的修改。

#### Q5 ★ RR 解决幻读了吗？

**参考回答**：不完全是。快照读靠 MVCC 看不到新插入；当前读靠 next-key lock 阻止范围内插入。但如果事务先快照读，别的事务插入提交，再执行 UPDATE 当前读，就可能作用到新行，之后快照读会看到它。

#### Q6 快照读和当前读的区别？

**参考回答**：普通 SELECT 是快照读，读历史版本，不加锁；`FOR UPDATE`、`FOR SHARE`、UPDATE、DELETE、INSERT 是当前读，读最新已提交版本并加锁。

#### Q7 ★ redo log 和 binlog 的区别？为什么要两阶段提交？

**参考回答**：redo 是 InnoDB 物理日志，用于崩溃恢复；binlog 是 Server 层逻辑日志，用于归档和复制。两阶段提交保证两者一致：redo prepare、binlog 落盘、redo commit；崩溃时根据 binlog 是否完整决定提交或回滚。

#### Q8 长事务有什么危害？

**参考回答**：锁持有时间长、undo 膨胀、purge 延迟、主从延迟、连接和内存占用，还可能阻塞 DDL。解决方式是缩短事务、拆分批量、事务内不做 RPC/文件 IO。

#### Q9 ★ `@Transactional` 什么情况下会失效？

**参考回答**：同类自调用、private/final 方法、异常被捕获、受检异常未配置 rollbackFor、异步线程、事务管理器不匹配、类没有被 Spring 代理等。

#### Q10 如何保证缓存和数据库一致性？

**参考回答**：常用 Cache Aside：读缓存，未命中查库回填；写先更新库，再删除缓存，并配合延迟双删或 binlog 订阅补偿。强一致通常要牺牲性能，多数业务接受最终一致。

### 2.9 易错点

- ⚠ “RR 完全解决幻读”是错的，快照读和当前读要分开讲。
- ⚠ MVCC 不只靠 undo，还需要隐藏列和 ReadView。
- ⚠ redo 不是 binlog；一个 InnoDB 层，一个 Server 层。
- ⚠ 隔离级别不是越高越好，Serializable 会大幅降低并发。
- ⚠ `@Transactional` 默认只回滚 RuntimeException/Error。
- ⚠ `readOnly=true` 不是“一定走从库”。

### 2.10 自测

1. RC 和 RR 的 ReadView 创建时机有什么不同？
2. 为什么 RR 下快照读看不到别的事务新插入的行？
3. redo 和 binlog 各自解决什么问题？
4. 两阶段提交的步骤是什么？
5. `@Transactional` 为什么同类自调用会失效？

<details>
<summary>参考答案</summary>

1. RC 每条快照读新建 ReadView；RR 第一次快照读创建并复用。
2. 因为 RR 复用第一次的 ReadView，新事务 ID 不在可见范围内。
3. redo 用于崩溃恢复和持久性；binlog 用于归档、复制和 PITR。
4. redo prepare → binlog 落盘 → redo commit；崩溃时根据 binlog 完整性决定。
5. Spring 事务基于代理，同类自调用不经过代理对象，注解不生效。

</details>

### 2.11 速记

- ACID：undo 原子、redo 持久、锁+MVCC 隔离、约束+应用一致。
- RR 默认；RC 常用于互联网业务。
- MVCC：隐藏列 + undo 版本链 + ReadView。
- RC 每条语句新视图，RR 复用第一次视图。
- 快照读不加锁，当前读加锁。
- redo 物理、binlog 逻辑、2PC 保证一致。
- 长事务：锁久、undo 胀、主从延迟。

## 3. 锁

### 3.1 一句话

InnoDB 的行锁加在索引上；索引决定锁的范围，隔离级别决定锁的算法。

### 3.2 锁的层次与类型

| 层次 | 锁 | 说明 |
| --- | --- | --- |
| 全局 | 全局读锁 | `FLUSH TABLES WITH READ LOCK`，备份用 |
| 表 | 表锁 | `LOCK TABLES ... READ/WRITE` |
| 表 | MDL 元数据锁 | CRUD 拿共享 MDL，DDL 拿排他 MDL |
| 行 | 共享 S / 排他 X | 行级读写锁 |
| 表 | 意向 IS / IX | 表示表内存在行锁，快速判断表锁冲突 |
| 行 | Record / Gap / Next-Key | InnoDB 行锁算法 |
| 行 | 插入意向锁 | 插入前在间隙上加 |
| 表 | 自增锁 | AUTO_INCREMENT 并发控制 |

**S/X 兼容矩阵**

| 已持有 \ 请求 | S | X |
| --- | --- | --- |
| S | 兼容 | 冲突 |
| X | 冲突 | 冲突 |

意向锁 IS/IX 之间兼容，但与表级 S/X 冲突；它们的作用是让表锁不必逐行检查。

### 3.3 行锁算法

假设索引上有值 5、10、15：

```
gap:      (-∞,5)   (5,10)   (10,15)   (15,+∞)
record:      5        10        15
next-key: (-∞,5]   (5,10]   (10,15]   (15,+∞)
```

- Record Lock：锁住某条索引记录。
- Gap Lock：锁住索引间隙，阻止插入；不锁记录本身。
- Next-Key Lock：Record + 前面的 Gap，RR 下范围查询默认使用。
- 插入意向锁：插入前在目标间隙加；多个插入意向锁兼容，但和 Gap Lock 冲突。

### 3.4 锁与索引的关系

| SQL | 锁范围 |
| --- | --- |
| `WHERE id=?`（主键/唯一索引等值） | 一条记录 |
| `WHERE id BETWEEN ? AND ?` | 范围 next-key |
| `WHERE age=?`（无索引） | 全表扫描到的记录和间隙，接近表锁 |
| `SELECT ... FOR UPDATE` 走索引 | 索引记录/范围 |
| `SELECT ... FOR UPDATE` 不走索引 | 大量记录/间隙 |

⚠ 面试高频：**InnoDB 锁的是索引，不是行本身**。没有索引时，扫描到哪些记录就锁哪些，范围可能非常大。

**当前读的语法**

```sql
SELECT * FROM sync_tasks WHERE id = 1 FOR UPDATE;
SELECT * FROM sync_tasks WHERE id = 1 FOR SHARE;

-- MySQL 8.0：拿不到锁立即返回 / 跳过已锁行
SELECT * FROM sync_tasks WHERE id = 1 FOR UPDATE NOWAIT;
SELECT * FROM sync_tasks WHERE status = 'TODO' FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` 常用于多消费者抢任务队列。

### 3.5 RC 与 RR 的锁差异

- RR：范围查询/锁定读通常使用 next-key lock，容易锁间隙。
- RC：普通查询和 DML 基本不使用 gap lock（外键约束检查和唯一性检查除外），死锁概率更低。
- 所以很多互联网业务选择 RC + row 格式 binlog。

### 3.6 死锁

四个必要条件：互斥、持有并等待、不可剥夺、循环等待。

```
T1: 锁 A → 等待 B
T2: 锁 B → 等待 A
```

- InnoDB 有死锁检测，发现循环等待会回滚“代价较小”的事务。
- 应用要捕获死锁异常（如 1213）并重试。
- `innodb_lock_wait_timeout` 默认 50 秒；超时会报锁等待超时。
- `innodb_deadlock_detect` 可以关闭，但高并发下要用超时和重试兜底。

**排查命令**

```sql
SHOW ENGINE INNODB STATUS\G
-- 看 LATEST DETECTED DEADLOCK

SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM information_schema.INNODB_TRX\G
```

**预防**

- 固定加锁顺序；
- 事务尽量短；
- 走索引，减少锁范围；
- 减少大范围 `FOR UPDATE`；
- 热点行拆分（库存分桶）；
- 失败重试 + 退避；
- 业务允许时用 RC。

### 3.7 乐观锁、悲观锁与分布式锁

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 悲观锁 | `SELECT ... FOR UPDATE` | 冲突多、强一致、事务短 |
| 乐观锁 | 版本号/CAS 更新 | 读多写少、冲突少 |
| 分布式锁 | Redis/ZK | 跨实例互斥 |

**乐观锁 SQL**

```sql
UPDATE sync_revisions
SET revision = revision + 1
WHERE user_id = ? AND revision = ?;
-- 影响行数为 0：版本冲突，重试或返回冲突
```

**库存扣减**

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ? AND stock >= 1;
-- 检查影响行数：1 成功，0 库存不足
```

这是单条 SQL 的原子操作，靠行锁保证不超卖；不要先查再改。

### 3.8 高频面试题

#### Q1 ★ InnoDB 有哪些锁？

**参考回答**：按粒度分全局锁、表锁、行锁；行锁有共享 S、排他 X；表级有意向锁 IS/IX 和 MDL；行锁算法有 Record、Gap、Next-Key；还有插入意向锁和自增锁。

#### Q2 ★ 什么是 next-key lock？解决什么问题？

**参考回答**：Next-Key Lock 是 Record Lock + Gap Lock，锁住记录及其前面的间隙。它在 RR 下用于范围查询/锁定读，阻止其他事务在范围内插入，从而避免当前读的幻读。

**追问**：RC 下还有吗？→ 普通查询和 DML 基本没有，外键和唯一性检查除外。

#### Q3 ★ 为什么没走索引会锁很多？

**参考回答**：InnoDB 行锁加在索引上。没有可用索引时，只能全表扫描，扫描到的记录和间隙都会被锁，效果接近表锁，严重阻塞并发写入。

#### Q4 意向锁的作用是什么？

**参考回答**：意向锁是表级锁，表示表内存在行锁。这样加表锁时不必逐行检查，只要看意向锁是否冲突即可。IS/IX 之间兼容。

#### Q5 RC 和 RR 的锁差异？

**参考回答**：RR 下范围查询/锁定读使用 next-key lock，容易锁间隙；RC 基本不用 gap lock（外键和唯一性检查除外），死锁更少，所以互联网业务常用 RC。

#### Q6 ★ 死锁怎么产生、排查、避免？

**参考回答**：多个事务以不同顺序持有并等待锁，形成循环等待。排查看 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK，或 `performance_schema.data_locks/data_lock_waits`。避免方法是固定加锁顺序、短事务、走索引、减少范围锁、热点拆分、失败重试。

#### Q7 `SELECT ... FOR UPDATE` 锁什么？

**参考回答**：它锁住扫描到的索引记录和间隙（RR 下）。走主键/唯一索引等值时锁一条；走范围锁 next-key；不走索引会锁大量记录，接近表锁。

**追问**：`NOWAIT` / `SKIP LOCKED`？→ 8.0 支持；拿不到锁立即返回或跳过，适合队列消费。

#### Q8 乐观锁和悲观锁的区别与场景？

**参考回答**：悲观锁先加锁再操作，适合冲突多、强一致；乐观锁用版本号/CAS，提交时检查冲突，适合读多写少、冲突少。乐观锁没有长事务锁等待，但冲突时需要重试。

#### Q9 ★ 如何实现库存扣减不超卖？

**参考回答**：用一条原子 SQL：`UPDATE product SET stock=stock-1 WHERE id=? AND stock>=1`，检查影响行数；不要先 SELECT 再 UPDATE。热点库存可以分桶、异步扣减或 Redis 预扣，但要处理一致性和回补。

#### Q10 MDL 是什么？长事务为什么阻塞 DDL？

**参考回答**：MDL 是元数据锁，CRUD 拿共享 MDL，DDL 拿排他 MDL。长事务一直持有共享 MDL，DDL 就要等待，后续请求可能排队，表现为“改表卡住”。

### 3.9 易错点

- ⚠ 行锁锁的是索引，不是“行本身”。
- ⚠ 没索引不是严格意义的表锁，而是锁大量记录/间隙，效果接近。
- ⚠ RC 不是完全没有 gap lock，外键和唯一性检查仍可能用。
- ⚠ 乐观锁不是“没有锁”，只是不在数据库持有长锁。
- ⚠ `FOR UPDATE` 不一定只锁一行，取决于索引和范围。
- ⚠ Gap Lock 锁的是间隙，不是不存在的“行”。

### 3.10 自测

1. 为什么说 InnoDB 的行锁加在索引上？
2. `WHERE age=25` 没有索引，RR 下会锁什么？
3. Record、Gap、Next-Key 的区别？
4. 死锁的四个必要条件是什么？
5. 乐观锁和悲观锁分别适合什么场景？

<details>
<summary>参考答案</summary>

1. 因为锁对象是索引记录/间隙；扫描路径决定锁范围。
2. 全表扫描到的记录和间隙，效果接近表锁。
3. Record 锁记录；Gap 锁间隙；Next-Key 是记录 + 前面的间隙。
4. 互斥、持有并等待、不可剥夺、循环等待。
5. 乐观锁适合读多写少、冲突少；悲观锁适合冲突多、强一致、事务短。

</details>

### 3.11 速记

- 行锁锁索引，索引决定锁范围。
- 主键等值锁一条，范围锁 next-key，无索引锁一片。
- RR 有 gap lock，RC 基本没有。
- 死锁：固定顺序、短事务、走索引、重试。
- 库存：一条 `UPDATE ... WHERE stock>=1`。
- 乐观锁版本号，悲观锁 `FOR UPDATE`。

## 4. 分库分表

### 4.1 一句话

分库分表是最后手段：先优化 SQL、索引、缓存、读写分离和归档；确定要分，再选分片键，并接受跨片查询、事务和扩容的复杂度。

### 4.2 决策树

```
单表太大 / 写入太高 / 连接打满？
├─ 否 → 索引、慢 SQL、缓存、读写分离、归档、分区表
└─ 是 → 能否垂直拆分？
        ├─ 能 → 按业务分库 / 冷热字段分表
        └─ 否 → 水平分表 / 分库
                → 选分片键
                → 选路由算法
                → 设计全局 ID
                → 处理跨片查询 / 事务 / 分页
                → 设计扩容和数据迁移
```

**经验值（不是硬规则）**

- 单表百万到千万级，配合好索引通常没问题；
- 上亿行、单表几百 GB、QPS/连接打满，再考虑水平拆分；
- 行大小、热数据比例、写入模式比“行数”更重要；
- 小项目不要为了“架构感”分片，运维成本会翻倍。

**先做的优化**

- 慢查询治理、索引优化；
- 缓存（Redis）、读写分离；
- 历史数据归档、冷热分离；
- MySQL 原生分区表（单实例内，便于管理和归档，但不解决单机瓶颈）。

### 4.3 拆分方式

| 方式 | 做法 | 解决的问题 | 代价 |
| --- | --- | --- | --- |
| 垂直分库 | 按业务拆（用户库、订单库） | 耦合、单库压力 | 跨库 JOIN/事务 |
| 垂直分表 | 冷热字段拆开 | 单表行太大 | 多次查询/组装 |
| 水平分表 | 同结构按行拆 | 单表数据量 | 跨片查询、路由 |
| 水平分库 | 拆到不同实例 | 单机连接/IO/CPU | 分布式事务、运维 |

实际项目经常组合：先垂直，再水平。

### 4.4 分片键与路由

**分片键选择标准**

- 高基数、分布均匀；
- 查询必带，尽量避免跨片；
- 业务上稳定，不频繁变更；
- 能兼顾主要查询维度。

**订单场景的两难**

- 按 `order_id` 分片：查订单详情快，但“我的订单”要跨片。
- 按 `user_id` 分片：查我的订单快，但按订单号查要跨片。
- 解决：基因法（`order_id` 里嵌入 `user_id` 后缀，按 user_id 路由）、映射表（order_id → user_id/shard）、异构索引（ES）。

**路由算法**

| 算法 | 优点 | 缺点 |
| --- | --- | --- |
| 取模 | 均匀、简单 | 扩容要迁移大量数据 |
| 范围 | 扩容容易、范围查询友好 | 容易热点 |
| 一致性哈希 | 扩容迁移少 | 实现复杂、可能不均 |
| 映射表 | 灵活、可人工调整 | 多一次查询、映射表本身要可靠 |

### 4.5 分片后的八大难题

| 问题 | 常见方案 | 注意点 |
| --- | --- | --- |
| 全局唯一 ID | Snowflake、号段模式、Redis INCR | UUID 随机，不适合 InnoDB 聚簇索引 |
| 分布式事务 | 避免跨片；本地消息表/Outbox；TCC/Saga/Seata；XA | 强一致代价高，多数业务最终一致 |
| 跨片 JOIN | 冗余宽表、ES、广播后内存归并、基因法 | 数据冗余要同步 |
| 跨片分页 | 各片取 `offset+size` 归并；游标分页 | 深分页成本高 |
| 跨片聚合 | 各片预聚合再汇总 | `avg` 要拆成 `sum/count` |
| 全局唯一约束 | 分片内唯一 + 独立唯一服务/Redis | 数据库无法跨片保证 |
| 扩容 | 双写 + 影子表 + 校验 + 切读 | 迁移期间要保证一致性 |
| 运维 | 分片 DDL、备份、监控、链路追踪 | 复杂度显著上升 |

### 4.6 中间件与 NewSQL

- **ShardingSphere-JDBC**：客户端 SDK，Java 项目常用，轻量，但和语言/框架绑定。
- **ShardingSphere-Proxy**：独立代理，多语言接入，多一层网络和运维。
- **MyCat**：较早的代理方案，社区活跃度需评估。
- **Vitess**：YouTube 系，Kubernetes 场景常见。
- **TiDB / OceanBase**：NewSQL，自动分片、强一致，但成本、运维模型和 SQL 兼容性要评估。

### 4.7 高频面试题

#### Q1 ★ 什么时候需要分库分表？

**参考回答**：先看数据量、行大小、QPS、连接数和磁盘 IO。百万到千万级通常先优化索引/缓存/读写分离；上亿行或单机资源打满，再考虑水平拆分。不要为了架构感过早分片。

**追问**：分区表算分库分表吗？→ 不算，分区表还是单实例，主要便于管理和归档，不解决单机瓶颈。

#### Q2 ★ 分片键怎么选？

**参考回答**：高基数、分布均匀、查询必带、业务稳定。用户中心按 user_id；订单按 order_id 但“我的订单”需要 user_id，可用基因法、映射表或异构索引。要接受一定范围的跨片查询。

#### Q3 分库分表后全局 ID 怎么生成？

**参考回答**：Snowflake（时间 + 机器 + 序列，注意时钟回拨）、号段模式（数据库/Redis 批量发号）、Redis INCR。UUID 可以做唯一标识，但随机写入会导致 InnoDB 页分裂，不建议做主键。

#### Q4 跨分片分页怎么做？

**参考回答**：各分片取 `offset+size` 条，内存归并排序后取全局前 N；深分页成本高，优先用游标分页 `WHERE id > last` 或业务限制。也可以把列表数据同步到 ES/宽表。

#### Q5 跨分片事务怎么处理？

**参考回答**：优先避免跨片事务，按同一分片键设计。必须跨片时，强一致可用 XA/2PC；多数业务用本地消息表/Outbox + 最终一致，或 TCC/Saga/Seata。要设计幂等和补偿。

#### Q6 分库分表后怎么扩容？

**参考回答**：双写新旧分片 + 影子表 + 数据校验 + 切读 + 清理旧数据；一致性哈希或范围分片迁移量更小，取模扩容最痛。迁移期间要有回滚方案。

#### Q7 分库分表、分区表、读写分离的区别？

**参考回答**：分区表单实例内切分数据，便于管理；读写分离解决读压力，不解决单表容量；分库分表是跨实例的水平扩展，解决容量和单机瓶颈，但带来分布式复杂度。

#### Q8 你的项目需要分库分表吗？

**参考回答**：按 Orbit 目前的数据量不需要。先做好索引、唯一约束和归档；`sync_tasks(user_id, client_id)` 的唯一索引保证幂等，按 user_id 查询也天然适合未来按用户分片。真要扩展，再考虑按 user_id 水平分片，而不是一上来上中间件。

### 4.8 案例：Orbit 扩展到百万用户

当前关键表：

- `app_users`：`username` 唯一索引；
- `sync_tasks`：`(user_id, client_id)` 唯一索引；
- `sync_revisions`：每个用户一行，推送时行锁串行化；
- `sync_goals`、`sync_stages`、`sync_habits`、`sync_habit_records`、`sync_growth_events`。

如果用户量增长：

1. 先按 `user_id` 归档冷数据，保留热数据；
2. 读多写少时加缓存/读写分离；
3. 真正需要水平扩展时，按 `user_id` 分片，所有同步表都带 `user_id`，保证同一用户的写落在同一片；
4. `client_id` 在分片内唯一，跨片不保证；全局 ID 可由客户端生成 UUID 或服务端 Snowflake；
5. `sync_revisions` 跟随用户分片，保持单用户串行；
6. 跨用户统计走离线数仓/ES，不在业务库做全量聚合。

### 4.9 易错点

- ⚠ 分表不一定提升性能，跨片查询和归并可能更慢。
- ⚠ 取模简单但不适合频繁扩容。
- ⚠ 分库分表不能替代索引和 SQL 优化。
- ⚠ 分布式事务不是必须强一致，多数业务最终一致。
- ⚠ UUID 可以唯一，但不适合做 InnoDB 聚簇主键。
- ⚠ 分片键选错，后期迁移成本极高。

### 4.11 速记

- 能不分就不分；先索引、缓存、读写分离、归档。
- 分片键：高基数、均匀、查询必带。
- 取模均匀但扩容难；范围易热点；一致性哈希迁移少。
- 八大难题：全局 ID、事务、JOIN、分页、聚合、唯一约束、扩容、运维。
- 订单两难：order_id 与 user_id，用基因法/映射表。
- Orbit 现在不需要分片，按 user_id 是未来方向。

### 6.2 隔离级别与锁速查

| 级别 | 快照读 | 当前读/范围 |
| --- | --- | --- |
| RC | 每条语句新 ReadView | 基本 record lock，无 gap（例外：外键/唯一性） |
| RR | 第一次快照读建 ReadView，复用 | next-key lock |
| Serializable | 读也加锁 | 共享 next-key |

### 6.3 术语表

| 术语 | 含义 |
| --- | --- |
| 回表 | 二级索引查到主键后，再查聚簇索引 |
| 覆盖索引 | 查询列全在索引里，不回表 |
| ICP | 索引条件下推，在引擎层过滤 |
| MVCC | 多版本并发控制 |
| ReadView | 判断版本可见性的快照 |
| Next-Key Lock | Record + 前面的 Gap |
| MDL | 元数据锁 |
| 2PC | 两阶段提交 |
| 基因法 | 把分片键编码进另一个业务 ID |
| 号段模式 | 批量领取 ID 区间，减少数据库访问 |
